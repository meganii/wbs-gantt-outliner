## 2. 見直しの結論（なぜ 3 層にしないか）

課題意識は次の 2 つでした。

1. 「実績を出さないのであれば、なぜ裏でデータとして持つ必要があるのか」
2. 「基準・予定・実績と 3 つの観点で見るべきか」

調査した結果、**層の数は「そのアプリが答える問いの数」で決まる**という結論に至りました。P6 / MS Project が 3 層なのは、彼らが**進捗報告（基準との差異）と再見積もり（残り期間方式）**まで担うツールだからです。このアプリ（WBS アウトライナー + ガント、表と Excel が主な成果物）には 2 層で足ります。

決め手になった観察は 2 点です。

- **Phase 1 の実装では、実績が入力しても何も起きない**（下の消費者マップ）。入力する場所と表示する場所（表・Excel）はあるが、予定にも進捗にもガントにも影響しない＝**飾り**になっていた。
- **進捗の記録が「進捗率（数値）」と「実績日付（日付）」の二重管理**になっていた。MS Project なら `%完了 = 実績期間 ÷ 期間` で実績から導出される関係が、今はつながっていない。

さらに、**遅れ（差異）の判断に実績日付は必須ではない**ことも確認しました。基準（当初計画）+ 現在の日程、または基準から求めた予定進捗率と進捗率の比較で「遅れている」は読めます（P6 の Schedule % Complete の考え方）。実績日付が必要になるのは「実際にいつ起きたかの記録」が要るときだけです。

**決定: 3 層にしない。** 「基準開始日 / 基準終了日（基準計画）」＋「開始日 / 終了日（現在の日程）」の 2 層に、進捗率を足す形へ移行する。

## 4. 2 層案（採用方針）

### 4.1 モデル

| 概念 | 実体 |
| --- | --- |
| 基準開始日 / 基準終了日（基準計画） | 「基準計画として登録」した時点のスナップショット。不変（更新 / 元に戻す / 削除はメニューから） |
| 開始日 / 終了日 | **現在の日程**。役割は進捗率で決まる（下の表） |
| 進捗率 | 入力値。日付の役割を決め、ガントの塗りになる |
| 期間 | 開始日〜終了日の稼働日数（自動計算）。**編集もでき**、入力すると開始日を固定して終了日を再計算する。実績期間・残り期間は導出 |

**進捗率による日付の役割**

| 進捗率 | 状態 | 開始日 | 終了日 |
| --- | --- | --- | --- |
| 0% | 未着手 | 予定（見込み） | 予定（見込み） |
| 1〜99% | 進行中 | **実績** | 予定（見込み） |
| 100% | 完了 | **実績** | **実績** |

### 4.2 一次情報による裏付け

- **Microsoft Project**: `Start` / `Finish` は **Scheduled（現在の日程）** であり、実績開始日を入力すると**予定開始日が実績開始日に合わせて動く**。`%完了 > 0` で実績開始日が未入力なら予定開始日を実績開始日に設定し、`100%` で実績終了日を予定終了日から設定する。つまり MS Project でも `Start` / `Finish` は「着工後は開始が事実、完了後は終了も事実」として読める。`Actual Start` / `Actual Finish` を別フィールドで持つのは**記録と差異計算（EVM）のため**で、表示・計算の骨格は 2 層案と同じ。
- **Primavera P6**: `Start` / `Finish` は現在の日程で、着工後は実績。P6 が別バーで持つ `Planned`（着工時に凍結）の役割は、2 層案では**基準**が近似する。`Actual` を別バーで描くのはバーの表示項目を Timescale で定義する P6 の流儀による。

### 4.3 規則（決定済み / 2026-10-18）

**決定の要旨**: 進捗率は**日付を書き換えない**（MS Project の `%完了` 入力と同じ）。日付が動くのは「開始日 / 終了日」または「期間」を編集したときだけ。実績期間・残り期間は**導出（表示のみ・入力不可・保存しない）**。食い違いは自動で直さない。

**一次情報（MS Project）の根拠**

- 恒等式: `%完了 = 実績期間 ÷ 期間 × 100`、`期間 = 実績期間 + 残り期間`
- `%完了` / `実績期間` / `残り期間` は「**1 つのフィールドにだけ入力し、入力したフィールドが他を再計算する**」（[Percent (%) Complete fields](https://support.microsoft.com/en-us/project/percent-complete-fields)）
- **終了日が動くのは期間が動いたときだけ**。`%完了` の入力では期間が変わらないので**終了日は動かない**（例: 期間 3 日のタスクに `%完了 = 100` → 実績期間 3 日、**実績終了日 = 予定終了日**）
- `%完了 > 0` → 実績開始日が未入力なら **実績開始日 = 予定開始日**。`%完了 = 100` → **実績終了日 = 予定終了日**（＝日付の値は動かず、役割だけが確定する）
- `残り期間` を編集すると `期間 = 実績期間 + 残り期間` に期間が更新される（＝このときだけ終了日が動く）。`実績期間 > 期間` なら期間を実績期間に合わせ、残り期間 0 / `%完了` 100
- 「完了した作業が未来に見える / 残り作業が過去に見える」状態を**そのまま残す設定**があり、食い違いを自動では直さない

**規則（このアプリで実装する内容）**

| # | 論点 | 決定 |
| --- | --- | --- |
| 1 | 進捗率を戻したときの事実 | **消えてよい**。`実績開始日 / 実績終了日` の裏方フィールドは持たない |
| 2 | 進捗率と日付が食い違ったとき | **自動で直さない**。進捗率は日付を書き換えない（どちらかを正として他を再計算しない） |
| 3 | 進捗率 > 0 にしたとき | 開始日は動かさず、**そのまま実績開始日とみなす**。着工が遅れた場合はユーザーが開始日を実際の着工日に書き換える |
| 4 | 進捗率 = 100 にしたとき | 終了日は動かさず、**そのまま実績終了日とみなす**。実際の完了日が違う場合はユーザーが終了日を編集する |
| 5 | 期間 / 実績期間 / 残り期間 | `期間` = 開始日〜終了日の稼働日数。**編集可**（入力すると開始日を固定して終了日を再計算 = 終了日を指定する代替入力。後述）。保存値は日付から再計算され、独立した第 2 の真実源にはしない。`実績期間` = 進捗率 × 期間、`残り期間` = 期間 − 実績期間（どちらも導出・表示のみ・入力不可・**保存しない**） |
| 6 | 親タスク | 開始 = 子の最小開始、終了 = 子の最大終了、進捗率 = 期間重み付け（現行どおり）。親の日付は「事実と見込みの混ざり」になるが、現在の日程として正しい |
| 7 | ステータス | **進捗率から導出**（0 = 未着手 / 1〜99 = 進行中 / 100 = 完了）。手入力しない（進捗率との二重管理をやめる） |
| 8 | 着手後 / 完了後の日付編集 | ロックしない（**常に編集可**）。入力は日付と期間の 2 経路（期間は終了日の指定方法の 1 つ）。ロックすると訂正できなくなるため。編集が「事実の書き換え」になる旨を UI で示すかは実装時に判断（必須ではない） |

**期間の扱い（2026-10-19 決定 / 案 A: 現状維持）**

- 「工数（日数）から終了日を算出したい」ケースがあるため、`期間` セルは**編集可**とする。入力すると開始日を固定して終了日を稼働日で再計算し、ガントバーも再描画する（MS Project の Duration と同じ）。
- `期間` は「終了日を指定する代替入力」であり、日付と独立した第 2 の真実源ではない。通常の日付編集後は稼働日数から再計算される。
- 既知の境界ケース（未修正・現状維持）: 開始日が非稼働日のとき / 期間 0 を入力したとき / v3 読み込みは保存済み `duration` を信頼する（再計算しない）。不整合が問題になったら別途対応する。

**この規則で残る割り切り**

- 進捗率を戻すと「実際にいつ終わったか」は復元できない（規則 1）
- `進捗率 80%` なのに終了日が過去、という状態も許す（自動では直さない）。気づけるようにするのは後続の「遅れ表示」
- 進捗率は数値の入力であり、日付からは導出しない（`基準日`（Status Date）を使う自動導出は将来の検討）

### 4.4 表・Excel・ガントへの影響

- **列**: 予定期間 / 予定日付 / 実績期間 / 実績日付 の 4 本 → **期間 / 開始日 / 終了日** の 3 本（+ 基準はメニューとゴースト、差異列は任意）。
- **Excel 出力**: 「日程 1 組（開始日 / 終了日 / 期間）+ 基準 1 組（基準開始日 / 基準終了日 / 基準期間）+ 進捗率」に整理する。アンバーは色の語彙として残したいので、**基準側の列グループに使う**想定（日程側は通常色）。実装時に最終確認する。
- **ガント**: バー = 開始日〜終了日（左端は着工後は実績）、塗り = 進捗率、ゴースト = 基準。実績専用バーは持たない。開始の遅れはバーの左端として自然に読める。

**命名方針**

- 日付の列名は「予定日付 / 実績日付」をやめて「**開始日 / 終了日**」にする。1 つのフィールドの役割が進捗率で変わるため、どちらかの名前を付けると嘘になる（MS Project も同じ理由で `Start` / `Finish` という中立名）。
- 行の名前は「**項目名**」（旧「タスク名」）。WBS の 1 行を「タスク」ではなく「項目」として扱う（2026-10-19 変更）。状態列の表示名は「**状態**」（旧「ステータス」）。内部の識別子（`taskName` / `status` / `deriveStatus`）は互換のため変更しない。
- 基準側は「**基準開始日 / 基準終了日**」。「**基準日**」を単独で使わない（MS Project の 基準日 = Status Date、P6 の データ日 = Data Date と衝突する）。
- 「予定」は列名から外し、「未着手のときの開始日 / 終了日は予定」という**状態の説明**に限定して使う。

## 6. 3 層案で得ていたもの / 2 層案で失うもの

| 観点 | 3 層案 | 2 層案 |
| --- | --- | --- |
| 入力の系統 | 予定と実績の 2 系統（どちらを編集するか迷う） | 日付は 1 系統（迷わない） |
| 事実の記録 | 実績が独立フィールドとして残る | 進捗率を戻すと消える（規則 1 で決定: 裏方フィールドは持たない） |
| 着工時の当初予定（P6 の Planned） | 基準と実績で近似できる | 基準のみ（Planned は持たない） |
| ガント | 予定バー + 実績表現が別途必要 | バー 1 本で完結 |
| 実装・移行 | 大きい（Phase 2 / 3 が残る） | 小さい（v1 から 1 段で畳める） |

失うのは「厳密な事実の証跡」と「着工時点の当初予定」ですが、どちらも必要になった時点で後から足せます（実績開始日 / 終了日を裏方フィールドで追加、基準計画の世代を増やす）。
